# 餐图云备份

## 部署准备

1. 对已执行 001、002 迁移的业务 MySQL，检查后执行 `src/main/resources/db/mysql/003_meal_photos.sql`。应用不会自动建表。先迁移再部署新版后端，避免文字同步访问新表失败。
2. 配置私有 COS 存储桶及服务端环境变量：`COS_ENABLED=true`、`COS_BUCKET`、`COS_REGION`、`COS_SECRET_ID`、`COS_SECRET_KEY`。临时凭据使用 `COS_SESSION_TOKEN`，需在过期前更新。数据库账号需具有新表的 SELECT/INSERT/UPDATE/DELETE 权限。
3. COS 凭据需允许目标桶 `private/users/*` 范围的上传、读取和删除。不要向小程序下发这些凭据。每次上传显式使用私有 ACL。
4. 部署后端并更新小程序。使用两个真实账号验证隔离，再用同一账号在不同设备验证备份恢复。此次本地检查使用模拟存储，尚未执行真实云端联调。

## 用户流程

在「我的 → 数据与隐私」先开启饭案云同步，再单独同意餐图云备份，点击同步。旧文字授权不会被升级为照片授权。上传上限为每张2MiB，每份最多3张，JPEG/PNG/WebP。每账号文件登记上限3000条（包含待清理文件）。

照片以文件编号关联饭案，不在 MySQL 保存 Base64、签名 URL 或本机路径。下载通过 `wx.cloud.callContainer` 调用鉴权后端，返回图片内容并写入本机文件目录；无需额外开放 COS 下载域名。复制照片链接不会绕过账号权限。

只同步已实际保存到饭案的照片，临时拍摄但未保存的照片不会备份。同步为手动触发；AI 分析上传不等同于云备份。暂停照片上传后仍可恢复已有照片。JSON 数据导出包含照片编号，不包含图片二进制。

## API

- `GET/POST /api/account/photos/consent`：独立照片授权，版本 `meal-photos-v1`。
- `POST /api/account/photos`：`recordId`、`mimeType`、`base64`，要求同时具有饭案与照片授权，返回 `fileId`。
- `GET /api/account/photos/{fileId}`：仅所属账号读取，返回 MIME 与 Base64。
- 原饭案同步接口在 `record.cloudImages` 保存最多3个 `{fileId,mimeType}`；服务端验证文件属于当前账号和当前饭案。旧客户端未提供该字段时保留原照片。

## 一致性与清理

上传前创建持久化登记，再在事务锁保护下写对象存储；失败不会影响本机照片。小程序缓存成功上传结果，重试不重复上传未过期的同一文件。饭案版本冲突保留本机内容，等待用户选择。

替换照片、删除饭案或注销账号，会在同一 MySQL 事务中标记待删除文件。文件表故意不依赖用户表的外键，以保留注销后的清理任务。用户注销提交后，相关文件不可通过业务接口访问。

服务运行期间每60秒处理最多30个清理任务；失败任务保留重试。未关联饭案的暂存上传超过24小时也会清理。容器缩容至零时不运行后台任务，下次启动后继续，因此物理删除不是即时完成；生产可为服务配置最小实例或接入外部定时触发以保证清理频率。COS 关闭或凭据失效时清理暂停，恢复后继续。

## 本地验证

- 小程序：上传与恢复、单独授权、失败重试、暂停后本机照片保留、同步去重、恢复失败重试、上传期间编辑保护。
- 后端：使用 H2 和模拟对象存储验证账号与饭案隔离、MIME 核验、独立授权、替换清理、删除失败重试、注销后清理任务保留、旧客户端兼容与孤立上传清理。
- 未验证线上 MySQL 方言执行、COS 权限和真机实际上传下载，发布前需完成联调。
